# SpecTrail v0.9 real-world Agent validation

Date: 2026-08-13

## Outcome

The planned fixed-vs-Agent quality comparison is blocked before quality can be
measured. SpecTrail v0.9 is installable and its deterministic recorded paths are
release-ready, but its live model contracts are not compatible with the real
OpenAI-compatible endpoint configured for this study.

The bounded Agent did not reach its first extraction attempt with any of six
available chat models tested against the production Planner prompt and strict
`agent_decision_v1` validator. The fixed pipeline also failed its first real
document because the live models returned a JSON array where the v0.9
extraction contract requires an object containing `items`.

The evidence supports this release-level conclusion:

- v0.9 does not yet demonstrate real-world value over the fixed pipeline.
- With the configured provider, live Agent orchestration is currently unusable;
  every tested model failed before the first tool invocation.
- Live fixed extraction is also provider-incompatible, so the study cannot
  fairly compare final requirement quality, grounding, or recall.
- Continuing across hundreds of long-document chunks would repeat a confirmed
  contract failure and consume tokens without producing comparable artifacts.

No compatibility adapter was introduced to make the result look successful.
Doing so would no longer test the released production path.

Tag `v0.9.0`, `origin/main` at release time, and the release wheel all resolve to
commit `990a84b12c7720679a44e71f61978894d4b67e3c`.

The release wheel SHA-256 is:

```text
5453c4356bde39a4711747a1f3c7f20c3269cbba2d22aed509089e016112553b
```

Before publication, the exact wheel passed fixed/mock extraction, Agent with a

## Method and stop rule

The intended production-path comparison used the same endpoint, extraction
model, temperature zero, strict validation, structured-if-available Evidence,
automatic chunking, 16,000-character base prompt budget, one overlap block,
and `fail_fast=false`. Run order was to alternate by case. The Agent retained
the released v0.9 allowlist and budgets.

Provider usage, wall time, pipeline time, retry count, Planner/tool sequence,
terminal reason, counts, requirement structure, and Evidence grounding were
instrumented without changing runtime decisions.

The predeclared practical stop rule was: do not run the full long-document
matrix if the production contract cannot produce a valid first Planner decision
or a parseable fixed extraction on the shortest positive-control document.
That rule triggered. It prevents a known failure from being multiplied across
the 113-page and 297-page PDFs.

## Observed production runs

### Configured model: DeepSeek-V4-Flash

On `openspec_conventions_md`, the Agent made one Planner call and then failed
with `AGENT_PLANNER_FAILED` before any pipeline attempt. The provider returned
130 characters and reported 1,560 total tokens over 17.3 seconds. Its JSON used
`action`, `tool`, and `arguments`, but omitted required decision fields including
`schema_version` and `reason`.

The paired fixed run made two extraction calls and failed both chunks with
`ModelResponseParseError`, ending as `ALL_CHUNKS_FAILED`. It used 13,101 tokens
over 132.2 seconds. Both responses were JSON arrays of candidate objects rather
than the required top-level object with `items`.

A repeat produced the same two failure classes, so this was not treated as a
single stochastic miss.

### Alternate model: Qwen2.5-72B-Instruct

The exact production Planner prompt again failed. The returned object was:

```json
{
  "action": "run_requirement_extraction",
  "args": {
    "chunking_mode": "auto",
    "max_rendered_prompt_chars": 32000,
    "overlap_blocks": 3
  },
  "schema_version": "agent_decision_v1"
}
```

The contract requires `action="invoke_tool"`, plus `tool`, `arguments`, and
`reason`. The Agent therefore failed after one Planner call, zero pipeline
attempts, 845 tokens, and 29.9 seconds.

The paired fixed run's first extraction call returned an array and failed
parsing after 68.9 seconds and 4,541 tokens. The second provider call timed out
at 180 seconds. The fixed run ended `ALL_CHUNKS_FAILED` after 249.5 seconds.

## Planner compatibility probe

The production Planner prompt and validator were then tested directly against
six models advertised by the configured endpoint. This was a decision-contract
probe, not a replacement Agent implementation.

| Model | Valid `agent_decision_v1` | Runtime result |
| --- | --- | --- |
| DeepSeek-V4-Flash | no | `AgentPlannerResponseError` |
| Qwen2.5-72B-Instruct | no | `AgentPlannerResponseError` |
| DeepSeek-V3.2 | no | `AgentPlannerResponseError` |
| GLM-5 | no | `AgentPlannerResponseError` |
| MiniMax-M2.5 | no | `AgentPlannerResponseError` |
| Kimi-K2-Instruct | no | `AgentPlannerResponseError` |

The failure is systemic enough that a 10-document Agent quality score would be
misleading: the observed Agent success rate is 0%, pipeline attempts are zero,
retry count is zero, and there is no Planner/tool sequence beyond an invalid
first response.

## Additional real-document defect

Nine documents completed parser and Evidence profiling. The NASA handbook
parsed into 6,735 blocks, but Evidence construction rejected it with:

```text
table evidence requires a table document block: blk_0355
```

This is a separate parser/Evidence identity defect. It would hard-fail both
fixed and Agent orchestration before a model call, so it remains a valid
real-world negative case for the rerun.

## Requested metrics status

| Metric | Result |
| --- | --- |
| Fixed success | 0/2 observed positive-control runs |
| Agent success | 0/2 observed positive-control runs; 0/6 Planner-model probes |
| Final requirement quality | not measurable; no validated final artifact |
| Evidence grounding | not measurable for live output; NASA Evidence build failed deterministically |
| Agent retries | 0; no model produced the first valid decision |
| Planner/tool sequence | invalid first Planner response; no tool started |
| Token usage | recorded above for every completed provider response |
| Elapsed time | recorded above for Agent, fixed, and each provider call |
| Terminal causes | `AGENT_PLANNER_FAILED`, `ModelResponseParseError`, provider timeout, NASA Evidence identity error |

There is deliberately no requirement-count or quality-proxy comparison. A zero
artifact cannot support a semantic quality claim, and the corpus has no
exhaustive gold requirements from which recall could be computed.

## Decision

Do not start v0.10 feature development, and do not claim that v0.9 Agent
orchestration adds real-world value yet.

The next work should be a narrowly scoped v0.9.x correctness effort:

1. Publish the complete `AgentDecision` schema to live models or use a provider
   capability that enforces the exact discriminated JSON object.
2. Enforce the extraction response as an object containing `items`, including
   provider-level structured output where supported.
3. Version both changed prompts and add live-provider conformance cases without
   weakening strict runtime validation.
4. Correct the NASA PDF table-block/Evidence mismatch.
5. Rerun this same SHA-locked corpus before changing the corpus or beginning
   feature work.

Only after that rerun yields paired artifacts should human reviewers score
semantic completeness, atomicity, testability, and false positives. Automatic
structure and grounding metrics can support that review, but must not replace
it.

## Reproduction

```bash
python scripts/fetch_real_world_agent_corpus.py
python scripts/evaluate_real_world_agent.py --profile-only

# Production live run. The logical endpoint ID is non-secret and keeps provider
# identity out of persisted URLs.
python scripts/evaluate_real_world_agent.py \
  --endpoint-id real-world-eval-v1 \
  --insecure
```

The evaluator writes raw runs, per-case results, provider usage, a JSON summary,
and a Markdown report below `outputs/real-world-agent-v1/`. Provider credentials
and endpoint URLs are never copied into evaluation artifacts.
