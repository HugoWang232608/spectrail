# SpecTrail v0.9 real-world Agent validation

Date: 2026-08-13

## Outcome

The released v0.9.0 baseline was blocked before quality could be measured.
Its live Planner and extraction prompts did not constrain the configured
OpenAI-compatible endpoint to the strict JSON shapes enforced by SpecTrail.
The NASA handbook also exposed an Evidence consistency defect for rejected PDF
table candidates.

The v0.9.x correctness patch resolves all three observed blockers without
loosening runtime validation. Live OpenAI-compatible calls now request a JSON
object, both prompts publish exact output shapes, the prompt versions and
recorded fingerprints are advanced, and expected-but-unavailable table
capability no longer masquerades as published table Evidence.

The same SHA-locked short Markdown case now completes in both modes. The Agent
also demonstrated the production recovery path that the original study could
not reach: partial extraction failure, inspection, argument change, retry, and
successful finish. This is a correctness confirmation, not yet a completed
10-document value study.

- Released v0.9.0 remains the immutable failed baseline described below.
- The correctness-patch working tree passes the full repository suite: 584
  passed and one skipped.
- On the production rerun, fixed completed with warnings and produced 7 fully
  grounded requirements; Agent completed after one retry and produced 12 fully
  grounded requirements.
- One case is insufficient to claim general Agent superiority. The remaining
  corpus still requires paired execution and manual semantic review.

No response aliasing, array auto-wrapping, or validator relaxation was added.

## Method and stop rule

The intended production-path comparison used the same endpoint, extraction
model, temperature zero, strict validation, structured-if-available Evidence,
automatic chunking, 16,000-character base prompt budget, one overlap block,
and `fail_fast=false`. Run order was to alternate by case. The Agent retained
the released v0.9 allowlist and budgets.

Provider usage, wall time, pipeline time, retry count, Planner/tool sequence,
terminal reason, counts, requirement structure, and Evidence grounding were
instrumented without changing runtime decisions.

The predeclared practical stop rule was: do not run the full long-document
matrix if the production contract cannot produce a valid first Planner decision
or a parseable fixed extraction on the shortest positive-control document.
That rule triggered. It prevents a known failure from being multiplied across
the 113-page and 297-page PDFs.

## Observed production runs

### Configured model: DeepSeek-V4-Flash

On `openspec_conventions_md`, the Agent made one Planner call and then failed
with `AGENT_PLANNER_FAILED` before any pipeline attempt. The provider returned
130 characters and reported 1,560 total tokens over 17.3 seconds. Its JSON used
`action`, `tool`, and `arguments`, but omitted required decision fields including
`schema_version` and `reason`.

The paired fixed run made two extraction calls and failed both chunks with
`ModelResponseParseError`, ending as `ALL_CHUNKS_FAILED`. It used 13,101 tokens
over 132.2 seconds. Both responses were JSON arrays of candidate objects rather
than the required top-level object with `items`.

A repeat produced the same two failure classes, so this was not treated as a
single stochastic miss.

### Alternate model: Qwen2.5-72B-Instruct

The exact production Planner prompt again failed. The returned object was:

```json
{
  "action": "run_requirement_extraction",
  "args": {
    "chunking_mode": "auto",
    "max_rendered_prompt_chars": 32000,
    "overlap_blocks": 3
  },
  "schema_version": "agent_decision_v1"
}
```

The contract requires `action="invoke_tool"`, plus `tool`, `arguments`, and
`reason`. The Agent therefore failed after one Planner call, zero pipeline
attempts, 845 tokens, and 29.9 seconds.

The paired fixed run's first extraction call returned an array and failed
parsing after 68.9 seconds and 4,541 tokens. The second provider call timed out
at 180 seconds. The fixed run ended `ALL_CHUNKS_FAILED` after 249.5 seconds.

## Additional real-document defect

Nine documents completed parser and Evidence profiling. The NASA handbook
parsed into 6,735 blocks, but Evidence construction rejected it with:

```text
table evidence requires a table document block: blk_0355
```

This was an Evidence validator defect, not a block-identity mismatch. Page 16
contains a process diagram that the PDF parser correctly rejected as unreliable
table-cell Evidence. The block recorded `table_cell` as expected but unavailable;
the validator incorrectly treated that expectation as if a table locator had
been published. The patch now reserves the table-block invariant for actual
table IDs, row ranges, cell IDs, or available `table_cell` capability.

After the fix, the full handbook passes Evidence consistency with 6,735 blocks,
297 pages, and 104 accepted tables. The resulting Evidence fingerprint is
`d87db805afc1769d7089924f8e7266cc28c90d9ea7a9988735dcb5d0f880bc28`.

## Correctness-patch production rerun

The rerun used the original `openspec_conventions_md` bytes, endpoint identity,
model, temperature, strict validation, Evidence policy, and timeout. Only the
correctness patch changed.

| Mode | Outcome | Requirements | Fully grounded | Provider calls | Retry | Wall time |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| fixed | `completed_with_warnings` | 7 | 7/7 | 2 | 0 | 249.2 s |
| Agent | `completed` | 12 | 12/12 | 7 | 1 | 411.9 s |

The Agent sequence was:

```text
run_requirement_extraction({})
→ inspect_extraction_result({})
→ run_requirement_extraction({"chunking_mode":"force","max_rendered_prompt_chars":32000,"overlap_blocks":1})
→ finish(completed)
```

The first attempt completed one extraction chunk and timed out on the other.
The Planner observed the warning, inspected deterministic artifacts, selected a
different bounded chunking strategy, and completed a one-chunk retry. All 12
final source quotes and locators passed exactly. Fixed retained the first
chunk's 7 validated requirements and finished with a partial-chunk warning.

Provider token totals are incomplete because timed-out calls have no usage
payload. The four successful Planner calls reported 7,419 tokens; successful
extraction calls returned valid top-level `{"items":[...]}` objects.

exhaustive gold requirements from which recall could be computed.

## Decision

The v0.9.x correctness blockers are fixed and the production recovery path is
now demonstrated. Do not claim broad Agent superiority from this one paired
case, and do not replace the remaining corpus run with the structural proxy.

The completed correctness work is:

1. Publish exact Planner decision shapes and request JSON-object responses.
2. Publish the exact extraction `{"items":[...]}` shape and request JSON-object
   responses.
3. Version both prompts and refresh immutable recorded fixture fingerprints.
4. Correct expected-versus-available PDF table capability validation.
5. Verify the full test suite, the complete NASA document, and one paired live
   production case.

The remaining work is the full paired corpus run followed by human scoring of
semantic completeness, atomicity, testability, and false positives. Automatic
structure and grounding metrics can support that review, but must not replace
it.

## Reproduction

```bash
python scripts/fetch_real_world_agent_corpus.py
python scripts/evaluate_real_world_agent.py --profile-only

# Production live run. The logical endpoint ID is non-secret and keeps provider
# identity out of persisted URLs.
python scripts/evaluate_real_world_agent.py \
  --endpoint-id real-world-eval-v1 \
  --insecure
```

The evaluator writes raw runs, per-case results, provider usage, a JSON summary,
and a Markdown report below `outputs/real-world-agent-v1/`. Provider credentials
and endpoint URLs are never copied into evaluation artifacts.
