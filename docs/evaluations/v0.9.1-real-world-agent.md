# SpecTrail v0.9.1 real-world Agent follow-up

Date: 2026-08-13

## Outcome

v0.9.1 fixes the live JSON-contract and PDF Evidence blockers found in the
v0.9.0 study. The configured OpenAI-compatible endpoint now returns strict
Planner decisions and top-level `{"items":[...]}` extraction objects that enter
the production validator. The 297-page NASA handbook also completes parser and
Evidence consistency checks.

The attempted 10-document comparison did not complete because the provider
entered a sustained outage during the fifth document. Nine orchestration-mode
runs completed across the first four paired documents plus the fifth Agent run.
After the fifth Agent Planner timed out, the first two fixed extraction chunks
also timed out at 180 seconds with no response bytes. The run stopped after
those three consecutive timeouts instead of sending the remaining known-invalid
requests. Partial artifacts were retained for resumable follow-up.

This follow-up supports three bounded conclusions:

- The v0.9.1 protocol fix works in production. Successful responses consistently
  used the strict JSON objects required by the runtime; the original bare-array
  and invalid-decision failures did not recur.
- Agent orchestration can add value when the failure remains recoverable. On
  OpenSpec it observed partial chunk failure, inspected artifacts, changed
  arguments, retried, and preserved seven fully grounded requirements while the
  paired fixed run failed strict validation.
- The current Agent is not generally superior. It adds a Planner availability
  dependency, cannot retry a strict aggregate `PipelineValidationError`, and
  spent extra calls on a document that correctly yielded no requirements.

## Method

The corpus, source hashes, endpoint identity, model, temperature, strict
validation policy, structured-if-available Evidence policy, 180-second provider
timeout, and base fixed chunking configuration are unchanged from the v0.9.0
study. Agent retained its frozen allowlist and two-attempt pipeline budget.

The complete corpus still contains 10 documents. This run completed four
paired cases and the fifth Agent case before the outage stop. It is therefore a
partial matrix, not a 10-document success-rate estimate.

## What the strict runtime rejected

The fixed OpenSpec run produced 27 candidates. Thirteen validated and thirteen
were quarantined, primarily because model-provided quotes did not occur in the
claimed blocks; strict policy therefore published no final artifact. Agent's
second attempt retained seven exact-grounded requirements and legitimately
finished with partial-chunk warnings.

Both CSV modes received valid JSON objects and 19 accepted model items. Fixed
had seven validated and twelve quarantined; Agent had nine validated and ten
quarantined. Typical failures were paraphrased or whitespace-altered quotes that
could not produce exact text locators. Both modes correctly failed strict
validation.

EU Age fixed completed 11 of 14 provider calls and formed 72 candidates, with
65 validated and seven quarantined. Agent selected a larger 32,000-character
strategy, completed four of seven chunks, and formed 29 candidates, with 23
validated and six quarantined. Both attempts ended in strict aggregate
`PipelineValidationError`, so neither exposed intermediate validated items as a
successful final result.

This failure class is currently non-recoverable in Agent runtime. Provider
timeouts can become a retryable ToolResult, but a later strict aggregate
validation failure hard-fails before the Planner can inspect and choose another
attempt. That boundary should be evaluated as a future correctness change, not
silently reclassified in this release.

## Agent sequences

OpenSpec:

```text
run_requirement_extraction({})
-> inspect_extraction_result({})
-> run_requirement_extraction({"chunking_mode":"force","overlap_blocks":1})
-> finish(completed_with_warnings)
```

Business requirements template:

```text
run_requirement_extraction({})
-> inspect_extraction_result({})
-> run_requirement_extraction({"chunking_mode":"force","overlap_blocks":1})
-> finish(completed_with_warnings)
```

The business template is a useful negative control: both extraction strategies
returned `NO_REQUIREMENTS_FOUND`. Agent used eight provider calls versus fixed's
two without improving the result.

CSV and EU Age each hard-failed after one extraction decision because strict
aggregate validation is non-recoverable. EUDI did not reach a decision because
the Planner call itself timed out.

## Manual sample review

All seven final OpenSpec Agent requirements were reviewed against the source.

- Grounding: 7/7 quotes are exact and point to the correct source blocks.
- Relevance and false positives: 7/7 represent explicit high-level SHALL
  requirements; no obvious false positive was found.
- Atomicity: the seven statements are individually reviewable, although some
  summarize broad formatting behavior rather than scenario-level obligations.
- Classification: functional/non-functional/constraint labels are plausible but
  not consistently compelling; classification quality needs a larger review.
- Testability: every `verification_method` is `unknown`, so the output is not
  ready to claim strong verification planning quality.
- Completeness: poor for the full document. The seven items cover high-level
  requirements from the first successful chunk but omit later scenario rules
  and later requirement sections after the failed chunk.

The sample demonstrates why exact Evidence grounding is necessary but not
sufficient. A perfectly grounded partial artifact can still have low recall.

## PDF verification

All three PDFs were reprofiled and representative pages were rendered and
visually checked.

- ReqView: 13 pages, 218 blocks, one accepted table. The revision-history grid
  is visually a true table.
- NIST IR 8214C: 113 pages, 1,688 blocks, zero accepted tables. A visually clear
  table on sampled page 20 is conservatively represented through text/page
  Evidence because the strict geometry proof did not accept it.
- NASA handbook: 297 pages, 6,735 blocks, 104 accepted tables. The page 16
  systems-engineering flow diagram remains a rejected table candidate, while
  the page 17 AS9100 alignment grid is correctly accepted as a table.

The NASA Evidence fingerprint remains
`d87db805afc1769d7089924f8e7266cc28c90d9ea7a9988735dcb5d0f880bc28`.

## Decision

v0.9.1 is suitable as a correctness release: installability, deterministic
gates, strict live JSON conformance, real recoverable retry behavior, and the
NASA PDF defect are verified. The release does not establish broad Agent value.

Before claiming that Agent mode outperforms fixed mode, resume the remaining
matrix when the provider is healthy, obtain complete paired artifacts, and
score semantic recall and testability across formats. Separately assess whether
strict aggregate validation failures with only grounding/locator quarantine can
safely become recoverable Planner observations.
